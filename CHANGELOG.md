# Changelog

## 0.2.1

Проверено на PHP 8.4 против текущего ядра MajorDoMo (`sergejey/majordomo`, ветка master).
Схема БД не менялась, существующие правила `optimizerdata` сохраняются.

### Критичные исправления

**Настройки по умолчанию терялись при установке.**
`install()` вызывал `saveConfig()` до `parent::install()`. Записи модуля в `project_modules`
ещё не существовало, `SQLUpdate()` формировал `UPDATE ... WHERE ID = ''` и не находил строку.
В результате после установки `DATA` оставался `NULL`, `START_DAILY` был пуст и ночная
оптимизация не запускалась никогда, пока администратор вручную не сохранит форму настроек.

**Фатальная ошибка под PHP 8 в `analyze()`.**
`usort($result['RECORDS'], ...)` при пустом наборе данных: под PHP 7 это notice,
под PHP 8 — `TypeError: usort(): Argument #1 must be of type array, null given`.
Воспроизводится при `SEPARATE_HISTORY_STORAGE=1` и на системе без истории,
то есть кнопка «Analyze data usage» просто роняла страницу.

**Уничтожение нечисловой истории.**
`array_sum()` по значениям вида `on`/`off` даёт `0`, и история затиралась нулями.
Замер на тестовых данных: из 1246 записей статуса 1104 превратились в `0`.
Отдельно опасно то, что `AUTO_OPTIMIZE` создаёт правило `avg` автоматически
для любого свойства, включая текстовые.
Теперь нечисловые серии не проходят через арифметику: сохраняется последнее
значение интервала. Добавлены явные режимы `MIN` и `LAST`.

**Неверная статистика при раздельном хранении истории.**
`$total_after` считался запросом `FROM phistory`, тогда как `$total_before` брался
из `$history_table`. При `SEPARATE_HISTORY_STORAGE=1` лог сообщал «удалено 17280»
при реальных 15653.

**`OPTIMIZE TABLE` внутри цикла вставки.**
Команда выполнялась после каждой агрегированной строки, а она перестраивает таблицу целиком.
Список затронутых таблиц теперь собирается и дефрагментируется один раз в конце прогона.
Замер A/B на одинаковых данных: 1344 вызова и 14.4 с против 1 вызова и 4.6 с
при побайтово идентичном результате.

**SQL-инъекции.**
`?object=` и `?property=` подставлялись в запрос без экранирования, `?id=` — без приведения
к числу. Добавлены `DBSafe()` и `(int)`.

**Запрос вида `VALUE_ID NOT IN (1,2,...)` со списком всех свойств.**
На крупной системе длина запроса превышает `max_allowed_packet`, `SQLSelectOne()` возвращает
`NULL`, а `current(NULL)` под PHP 8 даёт `TypeError`. Заменено на `NOT EXISTS (...)`.

**`optimize.php` был доступен по HTTP без авторизации** и запускал необратимую чистку истории.
Для web-запросов добавлена проверка авторизованной сессии (если в системе есть администратор).
Запуск из CLI не изменился.

### Совместимость с PHP 8

- Конструктор в стиле PHP 4 (`function optimizer()`) заменён на `__construct()`.
  Формально он работал за счёт shim'а в `lib/module.class.php`, но зависеть от него не стоит.
- Убраны обращения к неинициализированным ключам массивов и свойствам `null`
  (`$this->config[...]`, `$_GET['data_source']`, `$res[0]['ID']`, `$rec['ID']`,
  `$this->owner->name`) — под PHP 8 это Warning, а `load_settings.php` их не подавляет.
- `current(SQLSelectOne(...))` заменено на явные проверки `is_array()`: `SQLSelectOne()`
  возвращает `NULL`, если строк нет или запрос завершился ошибкой.
- `htmlspecialchars(null)` (deprecated с PHP 8.1) — приведение к строке.

### Отображение хода оптимизации

Кнопка «Optimize Now» выводила поток `dprint(".")`. Каждый такой вызов ядра печатает
`<pre>.</pre><hr/>`, 4 КБ пробелов и `window.scrollTo(0, document.body.scrollHeight)` —
отсюда бесконечная прокрутка пустых строк. Замер на базе из 23 тыс. записей: страница весила
10 513 401 байт, содержала 2501 горизонтальную линию и 2501 принудительную прокрутку.

Класс получил свойство `$progress` — `callable($event, array $data)`. Пока оно не задано
(запуск по расписанию из CLI), поведение прежнее: обычный текстовый вывод.
`optimize.php` подписывается на события и рисует страницу прогресса: шкала выполнения,
текущее свойство и этап, счётчики «было / стало / удалено», таблица изменённых свойств,
сворачиваемый подробный лог (прокручивается только он) и итоговая сводка.
Та же операция теперь — 18 250 байт и 64 события.

Дополнительно:

- из `admin()` убрана ветка `optimizenow`, отдававшая пустую страницу; кнопка в списке правил
  ведёт на `optimize.php?id=<ID>` — оптимизация одного правила с тем же отображением прогресса;
- `DebMes` по периодам пишется только когда что-то реально удалено (было четыре записи
  в лог на каждое свойство независимо от результата).

### Прочее

- `LIKE` заменён на `=` при поиске правил: `DBSafe()` не экранирует `%` и `_`,
  из-за чего объект с такими символами в названии подхватывал чужое правило.
- В выборку интервала добавлен `ORDER BY ADDED, ID` — без него «последнее значение интервала»
  не определено.
- Добавлен отсутствовавший шаблон `templates/optimizer/action_usual.html`: без него фронтенд
  модуля отдавал пустую страницу.
- Убрана ссылка на несуществующий `optimizerdata_view.html`.
- Валидация формы настроек (часы 0–23, неотрицательные значения) и обязательность поля
  «Свойство».
- Защита от создания дублирующих правил при автоматическом анализе.
